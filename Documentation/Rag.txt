# Complete RAG document ingestion architecture using Ollama, chunking and multiple vector databases

For your LangChain + Ollama + Gemma 3:4B application, I recommend building a reusable RAG ingestion pipeline that supports multiple document formats and multiple vector database configurations.

The important thing is to separate your RAG application into four independent components:

1. Document ingestion: Read PDF, Word, Excel, CSV, TXT, HTML and other documents.
2. Document processing: Clean text, split into chunks and attach metadata.
3. Embedding generation: Convert chunks into numerical vectors using Ollama.
4. Vector storage and retrieval: Store vectors in InMemory, Chroma, FAISS, PostgreSQL/pgvector, Pinecone, Qdrant or other vector databases.

You should be able to change the vector database without rewriting your document ingestion and chunking code.

## 4. Different chunking strategies

Chunking is one of the most important parts of RAG. You should not use the same strategy for every type of document.

Here are five useful approaches.

A. Recursive character chunking

Best starting point

Splits on paragraphs, newlines, spaces and finally characters.

Original document

"Java is a programming language. Java supports OOP. Java supports multithreading..."

Chunk 1

Java is a programming language. Java supports OOP.

Chunk 2

Java supports OOP. Java supports multithreading.

Typical starting configuration: 1000 characters, 200 overlap.

B. Token-based chunking

Splits based on token count rather than character count. Useful when managing LLM context windows and token budgets.

Example: 500 tokens per chunk, 75-token overlap.

C. Markdown header-based chunking

Splits according to headings such as `#`, `##`, and `###`. Useful for technical documentation, manuals and knowledge bases.

D. Semantic chunking

Splits according to changes in meaning using embeddings. Related paragraphs stay together even if their lengths differ.

More computationally expensive

E. Parent-child chunking

Creates small child chunks for accurate retrieval while retaining larger parent sections for answering. Useful for large technical manuals and lengthy business documents.

For your initial implementation, start with recursive character splitting. Add semantic and parent-child chunking when you have retrieval evaluation data to justify the extra complexity.

The standard LangChain splitter and document indexing approach is documented here: [LangChain knowledge-base guide](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/knowledge-base.mdx?utm_source=chatgpt.com).

## 9. Implement a vector database factory

This is the most important design decision: your RAG code should not know which database is being used.

Create `vectorstores/vector_store_factory.py`.

The following implementation supports:

- InMemory
- Chroma
- FAISS
- Qdrant Cloud / self-hosted Qdrant
- Pinecone Cloud
- PostgreSQL pgvector

Important implementation notes:

- The Pinecone index must already exist and its dimension and similarity metric must match your embedding model. `nomic-embed-text` normally produces 768-dimensional embeddings.
- For PostgreSQL, install and enable the `vector` extension. Use a PostgreSQL connection URL accepted by your installed `langchain-postgres` version.
- For Qdrant, the code creates the collection with the dimension reported by Ollama.
- InMemory loses everything when the application exits.
- Chroma and Qdrant support persistent storage.
- FAISS saves a local index. The example rebuilds it on ingestion; loading a saved FAISS index is a separate operation.

For a production ingestion pipeline, add a source-level delete-and-reindex process. Otherwise, when a document changes, old chunks can remain alongside new chunks.

## 13. Advanced RAG: Other approaches you should learn

Once your basic RAG pipeline works, these are the next techniques worth implementing.

| Approach               | What it does                                     | When to use                  |
| ---------------------- | ------------------------------------------------ | ---------------------------- |
| Basic RAG              | Retrieves similar chunks                         | General documents            |
| MMR retrieval          | Diversifies retrieved results                    | Similar/repeated documents   |
| Metadata filtering     | Filters by document, department, date            | Enterprise RAG               |
| Hybrid search          | Combines keyword and vector search               | Technical/business documents |
| Reranking              | Reorders retrieved chunks by relevance           | Better retrieval precision   |
| Parent-child retrieval | Retrieves small chunks, supplies larger sections | Large manuals                |
| Multi-query retrieval  | Generates alternative search queries             | Complex questions            |
| Semantic chunking      | Splits according to meaning                      | Long-form documents          |

### Example: MMR retrieval

Instead of:

```
retriever = vector_store.as_retriever(    search_kwargs={"k": 4})
```

Try:

```
retriever = vector_store.as_retriever(    search_type="mmr",    search_kwargs={        "k": 4,        "fetch_k": 20,        "lambda_mult": 0.5    })
```

MMR (Maximal Marginal Relevance) attempts to balance relevance with diversity.

### Example: Metadata filtering

Suppose you have uploaded multiple documents:

```
{    "file_name": "employee_policy.pdf",    "department": "HR",    "year": 2026}
```

You can use metadata filtering to restrict retrieval to particular departments or documents.

For Chroma:

```
retriever = vector_store.as_retriever(    search_kwargs={        "k": 5,        "filter": {            "department": "HR"        }    })
```

Metadata filter syntax differs between vector database providers. Also, enforce authorization at the retrieval layer; do not rely on a user-provided department filter as a security boundary.

## 15. A few important production improvements to make

Before using the code for real document collections:

1. Incremental ingestion: Don't rebuild the entire database every time the application starts.
2. Deduplication: Generate stable document and chunk IDs. In the example, I recommend replacing the SHA-256 ID generator with UUID5 IDs for compatibility with Qdrant's UUID point IDs.
3. Document updates: Delete the previous chunks belonging to a changed document before inserting its replacement.
4. Versioning: Track document version, ingestion timestamp and embedding model.
5. OCR: Add OCR for scanned PDFs.
6. Retrieval evaluation: Test whether the correct document chunks are retrieved, separately from whether Gemma generates a correct answer.
7. Security: Implement document-level access control, encryption and appropriate retention policies.
